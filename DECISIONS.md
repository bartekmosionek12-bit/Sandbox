point open. Defaults follow the rule "most conservative, fail-closed option".

## 0.3.0: bundled runtime, joblib, legacy HDF5

Owner request of 2026-10-18 (`pip install safeloadai` must be enough; joblib and legacy
Keras `.h5` supported; false positives re-measured). Defaults picked by Claude:

| ID | Default | Rationale |
|---|---|---|
| R1 | The runtime ships as its own package, `safeloadai-runtime` 0.1.0, holding the unmodified `python-3.12.0.wasm` as package data. `fetch_runtime.py` is the only code that downloads it; it checks size and sha256 and fails on a mismatch. The in-tree build backend refuses to build an sdist or wheel without a verified file and never downloads, so pip never fetches anything at install time (the sdist carries the `.wasm`). Supersedes C9. | Owner spec; one 26 MB pure-Python wheel works on every platform. |
| R2 | Resolution: `$SAFELOADAI_WASI_PYTHON` if set (and then nothing else, so a typo is not silently replaced), else `safeloadai_runtime.path()`. The hash is compared with safeloadai's own pinned copy, not the runtime package's constant. The runner child hashes the bytes it compiles once more and refuses on a mismatch. | A swapped or tampered runtime package cannot vouch for itself; the second hash closes the window between check and read at no extra cost (the runner already hashed the bytes for the compile-cache key). |
| R3 | Verified hashes are cached per process, keyed by (path, size, mtime_ns, inode, device). | Spec: keep scans fast; any rewrite of the file changes the key. |
| R4 | Integrity failure raises `RuntimeIntegrityError` out of `scan`/`safe_load`; the CLI prints it and exits 4. A missing runtime stays a SUSPICIOUS emulation layer with the reason and a pointer to `safeloadai doctor`. | Owner spec: never fall back to a verdict on a tampered runtime. |
| R5 | `wasmtime>=49.0.0,<50` (was `==49.0.0`): the major version the suite runs against; `doctor` flags anything outside it. | Patch releases of the tested major; a new major needs a test run first. |
| R6 | CI builds both wheels once, installs them into a fresh venv per job (the runtime only from the build artefact, `--no-index`), then blocks the network for the test process (Linux: network namespace; macOS: `sandbox-exec`; Windows: outbound firewall rule for the venv and base interpreters), proves the block with `tools/assert_offline.py`, and runs the suite with `SAFELOADAI_EXPECT_INSTALLED=1`, under which `conftest.py` refuses to test the source tree. `src/` is no longer on the pytest path. | Owner spec: test what users install, offline. |
| R7 | On Windows the compiled-module cache directory is trusted without a permission check. | Windows permissions are ACLs that `os.stat` does not report; the cache is under the user's profile, private by default. Without it every scan recompiles the runtime. |
| R8 | The deep-mode Docker backend still needs a source checkout (it builds its image from `docker/`); installed from a wheel it reports itself unavailable, which is SUSPICIOUS. | Unchanged behaviour, now stated; deep mode is opt-in. |
| J1 | The pickle walker is now a value-tracking machine (`static/pickle_vm.py`): inert stand-ins for every value, nothing imported or called. Streams a real unpickler rejects (stack underflow, missing memo key, missing MARK, protocol > 5, out-of-band buffers) are parse errors, so SUSPICIOUS. | Needed to read a NumpyArrayWrapper's state exactly; stricter than the old stack-shape walk (one hand-written test pickle was invalid and is fixed). |
| J2 | Frames are checked like the pure-Python unpickler: a FRAME before the current one ends, an opcode that crosses a frame end, a STOP or joblib array data before the frame end are errors. | Bytes inside a frame after STOP are skipped by real unpicklers; a sequential walk would read them. |
| J3 | joblib format, read from `joblib/numpy_pickle.py` 1.6.0: after BUILD on a `joblib.numpy_pickle.NumpyArrayWrapper` built by NEWOBJ with no arguments (or `copyreg._reconstructor(cls, object, None)`), the dtype comes from `numpy.dtype(descr, False, True)` + its BUILD state; non-object data is an optional padding byte + padding (when `numpy_array_alignment_bytes` is not None) and `prod(shape) * itemsize` bytes; object dtypes are a nested pickle read by a fresh plain unpickler. The layout code is one stdlib module (`shared/joblib_layout.py`) used by the walker, the sandbox and the loader. Unsupported layouts raise and the file is SUSPICIOUS. Supersedes C23. | Owner spec: skip by shape/dtype/order, never treat array bytes as opcodes. |
| J4 | Allowlist: `("joblib.numpy_pickle", "NumpyArrayWrapper")` only (plain data holder). No scikit-learn pair is added until a real benign file from the Hugging Face set needs it (Part D). | Owner spec: exact pairs, justified. |
| J5 | Parser differential: from the first array, the bytes are also read as a plain `pickle.load` would (same stack and memo, no array hook) until that reading fails. Its imports are scored like any import (a known sink is MALICIOUS), except that the reading stops at the first import whose top-level module is neither stdlib, nor a common ML package, nor importable here. | joblib files are pickles: a file safe under joblib's reading could run code under pickle.load. Stopping at an impossible import avoids false positives from names stitched together out of the outer memo (measured on sklearn models with object arrays). |
| J6 | Compressed joblib is decompressed on the host with the standard library codecs (lz4 with the optional `lz4` package), streaming, at most 1 GiB of output and at most 1000:1 once past 1 MiB, xz/lzma decoder memory capped at 256 MiB, exactly one stream (trailing data refused). The decompressed pickle goes to the sandbox as the artefact. | Decompression is not deserialisation; the WASI build lacks `_lzma`. Small high-ratio files are allowed because they cannot exhaust memory. |
| J7 | lz4 without the `lz4` package: SUSPICIOUS with the reason and the install hint (`safeloadai[lz4]`). | Owner spec. |
| J8 | Legacy joblib < 0.10: the `ZF` container is decompressed and walked; any `NDArrayWrapper`/`ZNDArrayWrapper` (side files) makes the file SUSPICIOUS. | Side files are other files, opened by name and read with `numpy.load(allow_pickle=True)`; one scan covers one file. |
| J9 | `safe_load` reads joblib with its own reader: the restricted `find_class` (the wrapper maps to an inert local class, so joblib is never imported), the same layout code, `numpy.frombuffer` for raw arrays, a restricted plain unpickler for object arrays, native byte order like joblib. | The loader must enforce the policy on its own; joblib's nested reader would otherwise unpickle object arrays without restriction in older versions. |
| H1 | Legacy `.h5` metadata is read by a stdlib HDF5 reader of our own (`shared/hdf5_meta.py`) running INSIDE the WASI sandbox (task `h5_meta`); the root attributes come back in nonce-authenticated records of at most 45 KiB each and are reassembled and length-checked on the host. No host subprocess, no h5py, no libhdf5. | Owner spec preferred a pure-Python reader in WASI. pyfive was evaluated and rejected: it needs numpy, which the WASI build does not have. The reader is about 770 lines and covers metadata only. |
| H2 | The reader follows HDF5 file format 3.0 for what libhdf5 writes: superblock v0-v3 (v2/v3 checksums), object header v1/v2 with continuations and lookup3 checksums, old-style groups (v1 B-tree, SNOD, local heap; the Symbol Table message wins over the parent's cached copy, as in libhdf5), compact link messages, attribute messages v1-v3, fixed and variable-length strings (global heap). Unknown message types, dense storage, shared root attributes and external/user-defined links are problems; anything unparseable raises and the file is SUSPICIOUS. | Exactness over coverage: a structure the reader does not model is never guessed. |
| H3 | Every object reachable by hard links is visited (header only) to refuse external data files and virtual datasets; soft links are counted, not followed; hard-link cycles are visited once. Dataset contents (including compact data inside a layout message) are never interpreted. Limits: 100,000 objects, 2,000,000 header messages, 200,000 B-tree nodes, 16 MiB per attribute, 64 MiB per heap, 512 MiB of metadata reads. | Owner spec: never read weights; limits on attribute size and object count. |
| H4 | Root attributes must be scalar strings without NUL bytes (h5py turns arrays into numpy arrays, which Keras cannot parse, and truncates variable-length strings at NUL); duplicates are problems. | The values must be what Keras would read; when readers could disagree, SUSPICIOUS. |
| H5 | tf.keras 2.x configs carry no `module`: such objects must use a class name from the explicit `KERAS2_CLASSES` set (Keras 3 classes plus listed Keras 2 built-ins and the `Custom>Adam`-style optimizer names tf.keras 2.11-2.15 writes). Objects with a `module` follow the `.keras` rules. Lambda: `function_type == "function"` (a name looked up in `config.module`'s globals) and a non-`__main__` globals module are findings (MALICIOUS for a dangerous module or name); `output_shape` code is a finding. Activation strings must be built-in. `training_config`: loss/metric strings and MeanMetricWrapper `fn` must be built-in names, classes go through the same walk. | Owner spec: explicit Keras 2 mapping, never prefixes; custom losses/metrics/optimizers SUSPICIOUS. |
| H6 | `__keras_tensor__` (the marker Keras 3 functional configs use for a layer input) is allowlisted; for a Lambda without `build_config` the emulator takes the input shape from that marker. | Found on the Keras 3 `.h5` fixture; it names no importable object. Also removes a false positive on Keras 3 functional `.keras` files. |
| H7 | Weights-only `.h5` (no `model_config`, e.g. `save_weights`) is CLEAN when the structure checks pass. | `load_model` refuses such a file and `load_weights` reads only arrays; no config means no code path. |
| H8 | `safe_load` does not load `.h5`. | Keras' legacy HDF5 loader has no safe mode equivalent we can rely on across versions. |
| H9 | Test fixtures are written by tf.keras 2.15, Keras 3.15 and h5py 3.16 (`tools/make_h5_fixtures.py`), payloads by editing the config of our own fresh file; the reader is checked against h5py's values on them and fuzzed with byte flips. | A reader tested only against its own writer proves little. |
| D1 | A torch zip member without a `.pkl` name is examined when it starts with PROTO 2-5. If it parses as a complete pickle with imports, it is reported ("pickle outside the .pkl members") and is at least SUSPICIOUS. | CVE-2025-1889: scanners that pick pickles by extension miss one a loader is told to open by name. Raw tensor storages that happen to start with those bytes do not parse as a complete pickle with imports. |
| D2 | The lab corpus carries marker rebuilds of public scanner bypasses: nullifAI, CVE-2025-1716/1944/1945/1889, `_osx_support`, `pydoc.pipepager`, `timeit`, `cProfile.run`, `functools.partial`, `operator.methodcaller`. It also carries the CVE-2024-3660 `.h5`/`.keras` Lambda rebuilds. | Owner spec: public examples through `scan()` only, with harmless markers. Each one stays as a regression test. |
| D3 | Evaluation runs under `evaluation/guard.py`, which refuses framework imports, `pickle.load(s)`, process creation (except the sandbox runner and the compared scanners) and non-loopback sockets. modelscan is not run on `.h5`. | Owner spec: an equivalent of the test guard. modelscan opens `.h5` with h5py in its own process on the host. |
| D4 | Remaining false positives are documented with the missing pair and a safety call (`evaluation/results/false-positives-*.md`). They are not added. | Owner spec: no automatic allowlist additions. |
| E1 | Release 0.3.0 together with safeloadai-runtime 0.1.0. Publishing uses PyPI Trusted Publishing, started by hand only (`workflow_dispatch`, testpypi or pypi, through GitHub environments). The runtime is uploaded first with `skip-existing`, and pre-release versions are refused. | Owner spec: prepare the workflow but do not run it. No API tokens. A reviewer on the "pypi" environment can gate real uploads. |
| E2 | `SECURITY.md`: every confirmed bypass is fixed together with a marker-payload regression test that stays in the suite. | Owner spec. |

## 0.4.0: allowlist growth, UNVERIFIABLE, update monitoring

Owner request of 2026-10-18 (grow the allowlist from the reviewed false-positive list,
an informed override for files the scanner cannot verify, automated update monitoring).
Defaults picked by Claude are marked "default".

| ID | Decision | Rationale |
|---|---|---|
| A1 | Every pair marked "safe" in `evaluation/results/false-positives-20261018.md` is added as an exact `(module, qualname)` pair, with a one-line justification in `allowlists.py`. `FunctionTransformer` and the bare `.h5` `LayerScale` stay out. | Owner spec. Each addition has a regression test that keeps the malicious variant flagged. |
| A2 | `numpy.random._pickle.__generator_ctor` is accepted only when every call matches numpy's own pickles: first argument a numpy bit-generator name or a `__bit_generator_ctor(<numpy bit-generator class or name>)` instance, second absent or `__bit_generator_ctor`. Using it any other way (NEWOBJ, BUILD, passing it as a value) is SUSPICIOUS. Default: the same check now also covers the already allowed `__randomstate_ctor` and `__bit_generator_ctor`. | All three call one of their arguments, which would make them call primitives for any other allowlisted callable. The check only tightens existing entries; no benign file changed. |
| A3 | A TFOpLambda passes when its op is on `TF_OP_ALLOWED`. Default: `keras.src.layers.core.tf_op_layer` is accepted as the exact pair with `TFOpLambda`, not as a module for every Keras class. LayerScale, `keras.src.ops.numpy.Add` and `Multiply` are exact pairs too (`KERAS_CLASS_PAIRS`). | Owner spec, made one step narrower: `Dense` from the tf-op module is still unknown. |
| V1 | Every reason has a category: MALICIOUS, RISKY or UNVERIFIABLE (`report.Category`). A reason is UNVERIFIABLE only when the code that raised it says so and names the exact item: a bare class in a Keras 2 `.h5`, an unknown Keras class, registered object, activation, loss or function, or a pickle global outside the allowlist that is not a known sink (and calls on it in emulation). Everything else, including any reason without a category, is RISKY. The verdict does not change. | Owner spec. Fail closed: a new code path that forgets to categorise cannot create an override. |
| V2 | Known gadgets outside the sink lists (`numpy.testing._private.utils.runstring`, `_osx_support._read_output`, `functools.partial` and others in `KNOWN_GADGETS`) are never UNVERIFIABLE. | The scanner knows what they do; an override must not be able to accept a public bypass. |
| V3 | Overrides are scoped: only a file whose every reason is UNVERIFIABLE; only the exact items named, all of them; only that file (a list applies to the one file being loaded, a mapping applies through its sha256, and the CLI needs `SHA256:ITEM` with several files). There is no accept-all switch. Every attempt, accepted or refused, is recorded in the Report: items, sha256, UTC time, how (`api`, `cli-flag`, `cli-prompt`). | A global or prefix acceptance would turn a one-off decision into a standing hole for every later file that uses the same name. The record lets a reviewer see later who accepted what for which bytes. |
| V4 | The CLI prompts only when stdin and stdout are both a TTY, never with `--json` or `--no-input`, and the default answer is No (EOF is No). Default: an accepted file counts as exit 0. | Owner spec: CI and scripts never get an implicit yes. |
| V5 | `safe_load` adds accepted pickle pairs to the restricted unpickler for that load only. A legacy `.h5` still has no loader after an override (H8). | The loader keeps enforcing the policy on its own. |
| V6 | The evaluation reports UNVERIFIABLE-only false positives as their own column, still counted as false positives. It also counts malicious lab files that are UNVERIFIABLE only (4 in this corpus before V7, 3 after). | An override is a user decision, not a lower false-positive rate. |
| V7 | An unknown object whose top-level module imitates an allowlisted one is RISKY, never UNVERIFIABLE, so no override can accept it (`static/lookalike.py`). Imitation means: the name starts or ends with an allowlisted top-level package of 4 or more letters (`kerasx`, `numpy_`, `sklearn2`), or with a shorter one plus `_` or `-` (`tf_evil_pkg`); or it is at most 2 edits (with transpositions) from one of 5 or more letters (`nunpy`); or it does so after folding homoglyphs (Cyrillic, Greek, fullwidth, `0`/`1`/`rn`). Only the top-level package is compared, since that is what an import loads; `mycompany.keras_layers` is not a look-alike. Default: a short list of real packages with such names (`torchvision`, `keras_hub`, `tensorflow_hub`, `numba`, `sympy` and a few more, in `GENUINE`) is exempt and stays UNVERIFIABLE; they are not trusted. | Owner decision 2026-10-18: a look-alike name is a signal of intent, not an unknown. The exemption keeps real ecosystem packages overridable; it never makes anything CLEAN. |
| V8 | A Keras class, function or registered name (`package>Name`) whose module is a sink module is a known sink (MALICIOUS, `keras_static._promote_sinks`); one whose name is a sink symbol (`pickle_static.is_dangerous_import`) or a known gadget is RISKY. Neither is ever UNVERIFIABLE. | Found in review of PR #7: `{"module": "subprocess", "class_name": "Popen"}` was UNVERIFIABLE only, so an override could accept it, while the pickle path already refused the same names. Keras imports the named object and calls it, which is the same call a pickle REDUCE makes. |
| U1 | Dependabot opens weekly PRs for pip and GitHub Actions. Actions are pinned by commit SHA within the major already in use (resolved from the action's release tags), with the version in a comment. | Supply-chain hygiene; a moved tag cannot change what runs. |
| U2 | Drift monitoring never auto-trusts. `upstream-drift` installs the latest upstream libraries, writes benign models, scans them and runs the suite. If anything drifts it opens or updates one issue. Its token can write issues and nothing else: no contents, no PRs, no allowlist edits, no auto-merge. `runtime-watch` only reads release metadata. Adding a name stays a reviewed human change with a regression test. | An allowlist entry is a trust decision about what code a loader may run. A bot that adds whatever upstream renamed would let a malicious upstream release, or a typosquat that appears in a benign file, trust itself. |
| U3 | tensorflow-cpu is optional in `upstream-drift`: if it does not install, Keras 3 runs on JAX and the run continues. | Owner spec; TensorFlow wheels lag new Python versions. |
| U4 | The runtime is updated only by the manual procedure in `docs/UPDATING_RUNTIME.md`: a new pinned sha256 checked by a person, a new `safeloadai-runtime` version, the full suite against installed wheels, evaluation before and after, and a new release. | The pinned hash is the trust anchor of the sandbox. |

## 0.5.0: every reading of a file, builtins rule, CRC rule, tune/held-out split

Owner request of 2026-10-19, after the 310-file Hugging Face run. Defaults picked by

## 0.7.0: false-positive reduction and beta release

Owner request of 2026-10-19 (after the 0.5.0 Hub run: held-out 150/502 by default).
Defaults picked by Claude are marked "default".

| ID | Decision | Rationale |
|---|---|---|
| F1 | UNSUPPORTED is a verdict of its own, between CLEAN and SUSPICIOUS in rank. A file gets it only when no reading exists at all (`parsing/views.find_views` finds no pickle, joblib, ZIP or HDF5 reading) and the bytes do not look like a ZIP archive the reader refuses. It is never CLEAN, `safe_load` never loads it, no override accepts it, and the CLI exits 5 for it (SUSPICIOUS 3 and MALICIOUS 1 take precedence). Any other finding next to it makes the file SUSPICIOUS (RISKY). Files that parse but look odd (trailing bytes, a refused archive, a broken HDF5 superblock, a ZIP that is neither Keras nor PyTorch) stay RISKY. The extension mismatch an UNSUPPORTED file always has is a note, not a second reason, and the emulation layer records "nothing to emulate" instead of a failure. | Owner spec. 33 of the 48 RISKY held-out files were OpenVINO, CTranslate2 or KenLM `.bin` files.
