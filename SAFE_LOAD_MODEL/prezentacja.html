1. Problem: Zatrute Modele AI (Supply Chain)

Pobieranie modeli z publicznych platform to obecnie standard w branży ML. Jednak formaty takie jak Pickle (.pkl) czy Keras (.keras) są podatne na krytyczne luki.

Podczas wczytywania modelu pozwalają one na RCE (Remote Code Execution).

  • Atakujący osadza złośliwy kod w wagach lub architekturze sieci.
  • Wystarczy jedna instrukcja, by infrastruktura badacza została przejęta.
  • Konwencjonalne skanery nie radzą sobie z logiką wewnątrz plików ML, traktując je jak zwykłe dane matematyczne.
# TRADYCYJNE PODEJŚCIE: import pickle # Ładunek złośliwy wykonuje się automatycznie! model = pickle.load(open('model.pkl', 'rb'))

2. Rozwiązanie: Safe Tensor Sandbox

Projekt dostarcza gotową do wdrożenia bibliotekę Pythona (Drop-in Replacement), która zastępuje standardowe metody wczytywania modeli, wprowadzając zautomatyzowaną warstwę analityczną działającą w tle.

# BEZPIECZNE PODEJŚCIE Z WYKORZYSTANIEM BIBLIOTEKI: from sandbox_rce import safe_load_model # Biblioteka izoluje, detonuje, ocenia i ładuje model. model = safe_load_model('model.pkl')
  • Zero konfiguracji dla dewelopera – proces sprowadza się do podmiany jednej funkcji.
  • Jeśli model jest bezpieczny -> wczytuje się natychmiast i zwraca czysty obiekt.
  • Jeśli model zawiera złośliwy kod -> wykonanie jest blokowane, a system generuje Szczegółowy Raport Bezpieczeństwa.

3. Architektura Hybrydowa (3 Warstwy Ochrony)

System wykorzystuje podejście hybrydowe, co zapobiega zjawisku "Sandbox Evasion". Złośliwy kod próbujący ukryć swoje działanie przed piaskownicą zostaje zatrzymany na etapie parsowania struktury.

WARSTWA 1: Analiza Statyczna (Parser)

Błyskawiczne filtrowanie kodu (bez jego uruchamiania). Skanowanie instrukcji wirtualnej maszyny (opcode) i importów, zapobiegając wykonaniu ukrytych operacji w pamięci.

WARSTWA 2: Dynamiczna Detonacja (Docker Sandbox)

Uruchomienie modelu w rygorystycznie odciętym kontenerze z nasłuchiwaniem na wywołania systemowe. System pozwala złośliwemu kodowi zaatakować w pełni wyizolowane środowisko.

WARSTWA 3: Ocena przez Sędziego LLM

Sztuczna Inteligencja analizuje intencje działania zarejestrowane w logach, co skutecznie eliminuje problem fałszywych alarmów (False Positives).

Warstwa 1: Inteligentny Parser Statyczny

Parser stanowi pierwszą linię obrony, tworząc ustrukturyzowany kontrakt danych dla modułu decyzyjnego AI.

  • Dla plików .pkl proces obejmuje odczyt surowego strumienia instrukcji (np. REDUCE) w poszukiwaniu prób wstrzyknięcia.
  • Dla modeli .keras analizowana jest struktura archiwum (ZIP) pod kątem wbudowanych warstw wykonujących kod bajtowy (np. Lambda).
  • Analiza przebiega z pominięciem groźnej deserializacji, minimalizując ryzyko infekcji.

Warstwa 2: Detonacja w Prawdziwym Sandboksie

Analizę statyczną można omijać za pomocą obfuskacji kodu (np. dynamiczne budowanie ciągów znaków). Aby temu zapobiec, zaimplementowano piaskownicę opartą na platformie Docker.

  • Biblioteka automatycznie inicjuje odizolowany kontener testowy:
  • --network=none : Zablokowana komunikacja sieciowa (obrona przed C2).
  • --read-only : Zamknięty system plików, weryfikujący intencje zapisu.
  • --cap-drop=ALL : Brak jakichkolwiek uprawnień na poziomie jądra hosta.

Wewnątrz środowiska testowego zastosowano mechanizm Monkey-Patching na kluczowych wektorach ataków (os.system, subprocess). Ruch systemowy jest rejestrowany, a następnie cały kontener ulega bezpowrotnemu zniszczeniu, pozostawiając infrastrukturę hosta nienaruszoną.

Warstwa 3: AI jako Zautomatyzowany Sędzia

Zamiast polegać na podatnych na omijanie, naiwnych regułach tekstowych (np. YARA), do oceny logów z izolacji włączono zaawansowany model językowy (LLM). Pozwala to na ocenę intencji kodu, nie tylko jego syntaktyki.

🛡️ Ochrona przed atakiem Prompt Injection:

Ponieważ dane do analizy generowane są bezpośrednio przez badany (potencjalnie złośliwy) kod, atakujący mógłby osadzić w modelu polecenia modyfikujące działanie samego Sędziego AI. Problem ten rozwiązano poprzez kryptograficzne oznaczanie danych wejściowych (unikalny nonce w każdym procesie). Model traktuje ten obszar jako wysoce nieufny, oflagowując ewentualne próby manipulacji jako injection_attempt_detected.

Wynik działania algorytmu jest standaryzowany poprzez JSON Schema (zwracając wartości: safe, suspicious, malicious).

4. Integracja w Potokach CI/CD (MLOps)

Mimo rygorystycznej oceny dynamicznej trwającej kilka sekund, system jest zoptymalizowany pod nowoczesne środowiska produkcyjne – ochronę realizuje się na etapie wdrożenia w potoku (np. GitHub Actions), gwarantując brak spadku wydajności aplikacji końcowej (Zero Overhead na produkcji).

Wymagania infrastrukturalne:

  • Python >= 3.10
  • Docker Daemon: Oś izolacji.
  • ANTHROPIC_API_KEY: Do pracy modułu AI. W przypadku jego braku, system bezpiecznie opiera się wyłącznie na heurystyce!

5. Roadmapa Rozwoju (Co dalej?)

Obecna architektura zapewnia wysoką skuteczność ochrony, bazując na sprawdzonych mechanizmach konteneryzacji. System został zaprojektowany z myślą o adaptacji do przyszłych standardów branżowych:

  • WebAssembly (WASM) / Pyodide: Planowane przejście z Dockera na wbudowany interpreter, ładujący modele w natywnie izolowanym silniku WASM. Standard WASI na poziomie samej architektury blokuje dostęp do systemu operacyjnego, redukując narzut czasowy izolacji do milisekund.
  • Tensor Steganography Detection: Skalowanie modułu heurystycznego wykrywającego kod ukryty w najmłodszych bitach (LSB) wielkich macierzy wag (float32).
  • Rozwój w kierunku AI Data Compliance: Rozbudowanie Sędziego LLM o skanowanie ładowanego modelu pod kątem zgodności z regulacjami (np. AI Act) – m.in. zautomatyzowane wyszukiwanie zaszytych danych wrażliwych (PII) lub wykrywanie tzw. zatrucia danych (Data Poisoning).
